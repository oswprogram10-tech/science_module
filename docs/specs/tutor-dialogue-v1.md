# 튜터 대화 v1: 학생 말에 반응하기

변인 실험 화면의 기기 안 튜터(사양 `tutor-on-device-v1.md`)가 학생 말을 받았을 때, **먼저 그 말에 반응하고** 다음 질문을 한다.

해결하려는 문제: 학생이 답을 써도 같은 질문이 돌아온다. 원인은 두 가지다.
- 모델 출력이 검사에 걸려 기본 질문으로 대신하는데, 상황이 같으면 직전과 같은 기본 질문이 나온다.
- 모델이 직전 질문을 되풀이한다.

## 0. 원칙

- **정답 판정은 앱이 한다.** 모델은 판정하지 않는다. 1.7B 모델이 틀린 생각을 맞다고 할 위험을 막는다.
- 확인은 **학생 자신의 실험 결과를 근거로** 한다. 결과로 확인되기 전에는 맞았다고 하지 않는다.
- 학생이 틀렸어도 "틀렸어요"라고 하지 않는다. 결과를 다시 보게 한다.
- 정답(결론)은 학생이 먼저 말하게 한다. 힌트는 단계를 밟고, 마지막 단계도 빈칸을 남긴다.
- 학생 말·힌트 단계·판정 결과는 기기 메모리에만 둔다. 저장하지 않고 수업 서버로 보내지 않는다.

## 1. 학생 말 나누기 (`classifyUtterance`, packages/tutor)

학생 말(`utterance`)은 다음 차례로 나눈다. 앞에서 걸리면 뒤는 보지 않는다.

1. `dont-know`: 정규화한 말에 아래 낱말 가운데 하나가 있다.
   - 낱말: 모르, 몰라, 글쎄, 헷갈, 어려워, 생각이안, 생각안나, 잘모르
2. `answer`: 실험의 `tutor.answers` 가운데 하나와 맞는다(§2).
3. `question`: `?`로 끝나거나, 의문사(왜, 어떻게, 무엇, 뭐, 어디, 언제, 몇, 어느)가 있고 "요"·"까"로 끝난다.
4. `other`: 나머지.

**정규화(`normalizeKo`):**
- 공백, 문장부호, 기호를 지운다.
- 소문자로 바꾼다.
- 같은 정규화를 keys와 not에도 쓴다.

## 2. 결론 맞히기 (`matchAnswer`)

`answerKeySchema`(packages/schema)를 쓴다. 필드는 `iv?`, `conclusion`, `keys`, `not?`, `confirm`이다.

**맞힌 것으로 보는 조건:**
- `keys`의 묶음마다 낱말 하나 이상이 정규화한 학생 말에 들어 있다(부분 문자열).
- `not`의 낱말은 하나도 없다.
- 여러 개가 맞으면 배열의 앞 것을 쓴다.

**결과로 확인되었는가(`evidenced`):**
- 시행 기록에 `analysis.kind === 'fair-test'`인 시행이 있다.
- 그 시행의 `ivKey`가 answer의 `iv`와 같다. `iv`가 없으면 아무 공정한 시행이나 된다.

**지금 알아보는 변인을 먼저 본다:**
- 지금 고른 조작변인(없으면 마지막 공정한 시행의 변인)을 `iv`로 가진 answer를 먼저 보고, 나머지는 배열 차례대로 본다.
- 같은 말이 여러 결론에 걸릴 때 엉뚱한 결론을 확인하는 일을 줄인다.

**반대 낱말·부정 안전장치(`contradicts`):**
- 낱말 목록이 반대 표현을 빠뜨려도 틀린 생각을 맞다고 확인하지 않게 하는 장치다. 틀린 생각을 굳히는 것이 가장 나쁜 결과이므로, 맞는 말을 놓치더라도(그때는 모델 질문으로 간다) 이쪽을 지킨다.
- 학생 말에 아래가 있는데 그 answer의 결론·keys에 같은 뿌리가 없으면 그 answer로 맞힌 것으로 보지 않는다.
  - 반대 방향 낱말: 적게·덜·작은·낮은·느린·약한·줄어·줄이·낮추·짧·차가·찬·멀·늦·빼·없애·열면·벗기·상관없·관계없·가벼·작게·낮게·아니 등
  - "그대로·똑같·비슷", 필요 조건을 뒤집는 "없어도·없이도·있어도"
- 부정(띄어 쓰거나 붙여 쓴 "안"·"못", "~지 않", "~지 못". 안쪽·안에·안경 등의 "안"은 빼고, 띄어쓰기가 있는 원래 말에서 본다)이 있으면,
  그 answer의 keys 가운데 부정이 든 낱말("안터", "안붙", "정확하지않")이 학생 말에 그대로 있을 때만 맞힘으로 본다.
  keys 어딘가에 "안"이 있다는 것만으로는 통과하지 않는다("뚜껑 덮으면 안 따뜻해요"를 막는다).
- 그래서 부정으로 말하는 것이 자연스러운 결론(예: "물이 없으면 싹이 안 튼다")은 keys에 그 꼴("안터", "안트")을 넣는다.
- `not`에 걸리는 말은 이 장치보다 먼저 `opposite`로 본다.

**반대 방향 감지(`opposite`):**
- `keys`는 모두 맞는데 `not`에 걸린 경우다.
- 이때는 `answer` 대신 `opposite`로 본다.

## 3. 반응 정하기 (`planTurn`, packages/tutor, 순수 함수)

입력은 다음과 같다.
- experiment(교사 덧씌우기를 적용한 것)
- 지금 상황(fromVariableRuntime 결과)
- utterance
- previousTutor
- hintLevel(0~3)
- fallback(기본 질문)

출력은 아래 표의 계획 하나다.

| 학생 말 | 계획 | 보이는 글 |
|---|---|---|
| 없음(새 상황) | `model` | 모델 질문. 걸리면 기본 질문 |
| `dont-know` | `hint` | 힌트 사다리(§4)의 다음 단계. 모델을 쓰지 않는다 |
| `answer` + 확인됨 | `confirm` | `confirm` 문장 + 이어 가기 질문(§5) |
| `answer` + 확인 안 됨 | `predict` | "그렇게 생각했군요. {iv}만 바꾸어 실험으로 확인해 볼까요?" (iv가 없으면 "실험으로 확인해 볼까요?") |
| `opposite` + 확인됨 | `recheck` | "결과표에서 {iv}만 다른 두 시행의 {dv}을(를) 다시 견주어 볼까요?" |
| `opposite` + 확인 안 됨 | `predict` | 위와 같은 예측 반응. 틀렸다고 하지 않는다 |
| `question` | `model` | 모델 답. 걸리면 "좋은 질문이에요. " + 기본 질문 |
| `other` | `model` | 모델 답. 걸리면 "말해 줘서 고마워요. " + 기본 질문 |

**자리표시 채우기:**
- {iv}, {dv}는 기존 기본 질문의 자리표시 채우기와 같은 방식으로 채운다(조작변인 이름, 종속변인 이름, 조사 처리).
- {iv}는 answer의 iv 또는 지금 고른 조작변인으로 채운다.

## 4. 힌트 사다리

`hintLevel`은 useModelProbe가 기기 메모리에 둔다. `dont-know`마다 1씩 올리고 3에서 멈춘다. 새 상황(turnKey가 바뀜)이면 0으로 돌아간다.

**공정한 시행이 아직 없을 때(설계 힌트):**
1. "괜찮아요. 먼저 바꿔 볼 조건을 하나만 골라 볼까요?"
2. "{iv}만 바꾸고 나머지 조건은 그대로 두면 어떨까요?"
3. "{iv}만 바꾼 시행을 하나 더 해 보고 {dv}을(를) 견주어 볼까요?"

**공정한 시행이 있을 때(해석 힌트):**
1. "괜찮아요. 결과표에서 {dv} 칸을 볼까요?"
2. "{iv}만 다른 두 시행에서 {dv}은(는) 어떻게 다른가요?"
3. "{iv}이(가) 달라질 때 {dv}은(는) 어떻게 되었나요?"

3단계에서 또 모르겠다고 하면 3단계를 다시 보이지 않는다. 대신 "결과표의 두 줄을 손가락으로 짚어 보며 다시 볼까요?"를 보인다.

## 5. 맞혔을 때 이어 가기

**보이는 글:** `confirm` 문장 + 이어 가기 질문. 둘 다 앱이 만든다. 모델은 쓰지 않는다.

**이어 가기 질문:**
- 아직 공정한 시행으로 알아보지 않은 다른 조작변인이 있으면: "이번에는 {다른 iv}을(를) 바꾸면 어떻게 될지 알아볼까요?"
- 없으면: "이 결과를 생활 속 어디에서 볼 수 있을까요?"

`confirm`은 콘텐츠(또는 교사 덧씌우기)에서 온 앱 문장이다. 그래서 모델 출력 가드(forbiddenAnswers 등)를 거치지 않는다. 학생 말을 담지 않으므로 개인정보 문제도 없다.

## 6. 되풀이 막기

**모델 출력이 직전과 너무 비슷하면 실패로 처리한다.** 이유는 `repeat`, 결과는 대신 보이기다. 아래 가운데 하나면 실패다.
- 정규화한 문자열의 유사도(LCS 길이 / 긴 쪽 길이)가 0.8 이상이다.
- 마지막 질문 문장이 직전과 같다.

**앱이 만든 반응(예측·다시 보기·확인)이 직전에 보인 글과 같으면** 첫 문장은 두고 질문만 아래 대체 질문으로 바꾼다. 힌트 마지막 말("손가락")은 되풀이해도 된다.

**최종 글이 직전에 보인 글과 같으면** 다음 대체 질문 가운데 직전과 다른 첫 질문으로 바꾼다. 반응 접두어는 그대로 둔다.
- "그렇게 생각한 까닭을 말해 줄래요?"
- "결과표에서 어느 칸을 보면 그 생각을 확인할 수 있을까요?"
- "다음 시행에서는 무엇을 바꿔 보고 싶나요?"

## 7. 교사 고치기

- `TutorEdits`의 실험 항목에 `answers?: AnswerKey[]`(최대 8, 전체 바꾸기)를 더한다.
- 교사 화면 「튜터 질문 고치기」에서 실험마다 다음을 고칠 수 있다.
  - 결론
  - 낱말 묶음(묶음은 줄로, 낱말은 쉼표로)
  - 제외 낱말
  - 확인 문장
- 고친 것은 기존 덧씌우기처럼 학생에게 보낸다.
- 확인 문장에는 판정 낱말(정답, 틀렸, 맞았, 잘했어, 오답)을 쓸 수 없다. 화면에서 막는다.

## 8. 시험용 상태 표시

- 빌드 변수 `VITE_TUTOR_DEBUG=1`일 때만 튜터 칸 아래에 작은 글씨로 보인다.
- 보이는 것은 계획 종류와 이유다. 예:
  - 「모델 질문 · 0.9초」
  - 「기본 질문 · 되풀이」
  - 「힌트 2단계」
  - 「맞힘 확인」
- 학생 말은 보이지 않는다.
- CI의 안드로이드 debug APK 빌드에만 켠다. 출시 빌드에는 넣지 않는다.

## 9. 콘텐츠

- 변인 실험 46개의 manifest `tutor.answers`를 채운다.
- 보통 `forbiddenAnswers` 하나마다 answer 하나를 만든다.
- 확인 문장 형식: "네, 결과표에서도 …했어요."
  - 앱은 그 변인의 공정한 시행이 있는지만 본다. 학생이 어떤 값을 견주었는지는 모르므로 **숫자·단위·특정 수준을 쓰지 않고 상대 표현으로 쓴다**(예: "더 많이 감쌀수록 물이 덜 식었어요").
  - 결과를 근거로 한다.
  - 판정 낱말을 쓰지 않는다.
  - 80자 이하이고 마침표로 끝난다.
- 표현 시험 자료 `packages/tutor/src/answerKeys.fixture.json`에 answer마다 다음을 둔다.
  - 맞혀야 하는 학생 말 3개 이상(초등학생 말투, 띄어쓰기·맞춤법이 틀린 것 포함)
  - 맞히면 안 되는 말 2개 이상(반대 방향, 다른 변인)
- 방향이 있는 결론의 원인 묶음에는 명사만이 아니라 방향을 나타내는 낱말(덮·많이감·높·크·세게·가까·직렬 …)이 있어야 한다. 명사만 두면 "뚜껑을 열면 …"도 맞는다.

## 10. 버전

- `TutorEdits`의 실험 항목에 `answers`가 생겼다. 엄격한 스키마라서 이 필드를 모르는 옛 수업 서버·학생 앱은 `answers`가 든 튜터 덧씌우기 메시지 전체를 받지 않는다.
- 교사 PC 수업 서버(exe)와 학생 앱은 함께 올린다. 옛 학생 앱이 섞여 있으면 결론을 고치지 않은 상태로 두면 질문 덧씌우기는 그대로 간다.
